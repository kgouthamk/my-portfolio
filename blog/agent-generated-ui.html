Beyond the Chat Box:
The Case for Agent-Generated UI

Chat is the lowest common denominator of AI interfaces. It's where AI products go when their teams haven't yet figured out what the experience should actually be. The next frontier isn't a better chatbot — it's an agent that generates the right interface for every surface, every user, and every moment.

Why Chat Falls Short

When AI products default to chat, it's not a design decision — it's an admission of uncertainty. Chat is flexible enough to handle anything, which means it's optimized for nothing.

Consider a healthcare context. A user asks their AI health coach about managing their diabetes. A chat interface returns several paragraphs of text: current HbA1c, recommended targets, medication reminders, lifestyle suggestions. The user reads it, processes it, tries to remember it — and most of it is lost by the time they close the app.

Now imagine the same information rendered as a structured dashboard: a trend line for HbA1c over 6 months, a visual medication schedule, a progress ring for today's steps, and a single clear next action. The information is identical. The outcome is not. Rich, visual structure reduces cognitive load, improves recall, and — in healthcare — demonstrably improves adherence.

Chat was never the destination. It was the MVP while we figured out the real product.

What Agent-Generated UI Is

Agent-Generated UI (AG-UI) is the idea that an AI agent, given semantic intent about what it wants to communicate, can select and populate the right UI component for that content — without a human specifying the template in advance.

The key distinction from traditional dynamic UI: in AG-UI, the agent isn't filling slots in a predefined template. It's reasoning about the semantic structure of the content — "this is a medication schedule," "this is a trend over time," "this is a binary decision the user needs to make" — and selecting the appropriate representation from a registered design system of components.

This requires three things working together:

  • Semantic intent: The agent outputs structured intent about what the content is, not just what it says.
  • A component library: A registered set of UI components (following your design system) that can represent different content types — cards, timelines, progress trackers, decision trees, data tables.
  • Deterministic data hydration: The actual data that populates those components comes from verified sources — not inferred by the model. This is the critical safety mechanism that separates safe AG-UI from dangerous hallucination.

The Accuracy Problem — and How to Solve It

The reason most teams haven't built AG-UI yet is the fear that's completely legitimate: if the model is generating the UI, what stops it from populating a medication card with the wrong dosage? In healthcare, that's not a UX failure — it's a patient safety event.

The answer is to separate what the model decides from what the model generates:

  • The model decides intent: "Display the user's current medication schedule."
  • The system retrieves the data deterministically from a verified source (the EMR, the benefits system, the care plan).
  • The component is populated from that retrieved data — the model never touches the values.
  • Evals and hooks validate that the displayed content matches what was retrieved before rendering.

The result: the richness and adaptability of AI-generated UI, with the accuracy guarantees of a traditional data-driven interface. The model contributes intelligence about presentation — not facts about reality.

The safety principle: In AG-UI, the model's job is to select and structure — never to generate factual content. Data comes from verified sources. The model is the curator, not the source of truth.

The Omnichannel Imperative

AG-UI becomes transformative when you extend it across surfaces. Users don't live in your app. They're in SMS threads, WhatsApp groups, email, voice assistants, and third-party chat platforms. An AI health coach that's only available in-app reaches users when they choose to open it. An omnichannel agent reaches them where they already are — which is where behaviour change actually happens.

The challenge: each surface has fundamentally different rendering capabilities. Here's what an intelligent agent needs to account for:

Surface UI Capabilities Agent Adaptation
In-App (native) Full UI SDK, rich components, animations Rich card widgets, interactive elements, full design system
Email (HTML) HTML/CSS (limited), no JavaScript Structured HTML tables, inline styles, clear CTAs
SMS / MMS Text, limited MMS media Concise text with key numbers; MMS image for charts
WhatsApp / Messenger Platform-native cards, buttons, lists WhatsApp list messages, quick reply buttons, media cards
Chat Apps (Claude, Gemini) Markdown, code blocks, artifacts Structured markdown, formatted tables, clear hierarchy
Voice / VoIP Audio only — no visual Spoken summaries; key numbers verbalized; no lists
Push Notifications Short text, title + body, action buttons Single insight + single action; urgency-appropriate tone

A well-architected omnichannel agent doesn't just send the same content to every surface. It reasons about which surface the user is on, what that surface can render, and what the most effective representation of the content is for that context. A medication reminder in voice is a spoken sentence. In-app, it's a visual timeline with a check-off button. In SMS, it's a single line with a Y/N reply prompt. Same intent. Completely different experience.

"The omnichannel agent doesn't wait for users to open the app. It meets them in the moment they're already in — and speaks in the language of that surface."

The Protocols Making This Possible

Two emerging protocols are making AG-UI more tractable at scale:

AG-UI is an open protocol for streaming rich agent interactions — it defines how agents communicate their UI intent in a structured, serializable way that can be consumed by front-end renderers. This makes it possible to decouple the agent's reasoning from the rendering layer, which is essential for omnichannel deployment.

A2UI (Agent-to-UI) is a complementary standard for mapping agent semantic intent to design system components. A common misconception — one I've had to correct in engineering reviews — is that A2UI is tied to a specific design system (it isn't). It's a protocol layer. Your design system sits above it; A2UI provides the bridge between agent intent and component selection.

Together with MCP for tool access, these protocols form the foundation of what will become standard architecture for intelligent, multi-surface AI products over the next two to three years.

What to Build Now

AG-UI is still early. Most teams haven't implemented it. That's an opportunity — but only if you start building the foundation now:

  • Audit your design system for component semantics. Every component should have a clear semantic type — not just a visual name. "Medication card" not "info-card-variant-3." Agents need to reason about components by what they represent, not how they look.
  • Separate intent from data in your agent outputs. Start structuring your agent responses to include semantic intent alongside content. This is the architectural prerequisite for AG-UI.
  • Build surface-awareness into your agent architecture. The agent should know which surface it's rendering for. Start with two or three surfaces and add more. Don't try to support all seven simultaneously on day one.
  • Invest in evals for rendering accuracy. Test that the right component is selected for the right content type, and that data hydration is accurate. Rendering evals are different from response quality evals — don't conflate them.

The teams who start building this infrastructure today won't just have a better product. They'll have a platform that can adapt to surfaces and interaction patterns that don't exist yet — because the architecture is built for surface-agnostic intelligence, not for any specific rendering environment.

The chat box was where we started. It shouldn't be where we stop.
